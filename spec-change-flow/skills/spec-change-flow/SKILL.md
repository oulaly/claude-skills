当用户提出新需求、功能变更或技术改造（而非 typo 级小修）时，按本流程执行。核心原则：**先充分讨论、再规范、后编码、测试驱动、文档同步、验证闭环**。

## 1. 变更包（唯一源）

每个需求/变更的全流程文档放在 `docs/changes/<slug>/`（slug 为小写中划线，如 `portal-runtime-config`），该目录是该变更的**唯一源**。

固定四份文档：

| 文档 | 内容 | 编号 |
|------|------|------|
| `analysis.md` | 方案分析：问题定义、可选方案对比、结论 | ANALYSIS-\*-001 |
| `prd.md` | 产品需求：功能需求、用户故事、验收条件 | PRD-\*-001 |
| `design.md` | SPEC + 设计 + 测试验证（默认合并；大型需求可拆 `spec.md` + `design.md`） | DESIGN-\*-001 |
| `tasks.md` | 任务清单：按角色拆解、带状态标记 | TASKS-\*-001 |

测试规模较大时拆出第五份 `tests.md`（TST-\*-001）。

## 2. 变更分级

| 级别 | 范围 | 流程 |
|------|------|------|
| 豁免级 | typo、格式化、注释等低风险小修 | 直接改，不建变更包 |
| 标准级 | 单仓功能变更 | 完整四件套 + 多角色分工 |
| 重大级 | 跨仓、权限/安全、部署拓扑、API 契约变更 | 标准级 + 冻结点**强制人类确认** |

## 3. 角色分工

| 角色 | 职责 |
|------|------|
| 产品分析师 | `analysis.md`、`prd.md`（FR/US/AC） |
| 架构师 | `design.md`：技术方案、接口、数据模型、**指标清单**（SLI/SLO、指标名/类型/标签、告警阈值；必填节，无指标需求也须显式说明） |
| 开发工程师 | 源码实现 + 单元测试 + 指标埋点，执行 `tasks.md` 开发项 |
| 测试工程师 | `tests.md`、集成/E2E 测试、测试报告 |
| 运维工程师 | 部署目录、Dockerfile、编排/配置中心、监控部署、部署验证 |
| 质量合规审查员 | 文档一致性 + 安全合规（密钥/权限/CORS/日志脱敏）+ 质量门禁；design 冻结前预审、合并前终审 |
| 协调员（主 agent） | 任务拆解、`tasks.md` 状态维护、阻塞升级、workflow 编排 |

> 监控与指标不另设角色：架构师定契约（design.md 必填节）、开发埋点、运维接线部署、审查员核对一致性，防止埋点烂尾。

## 4. 协作规则（必须遵守）

1. 上游交付物未冻结，下游不得开工。冻结 = `prd.md`/`design.md` 确认 + `tasks.md` 由协调员生成。
2. 冻结确认双轨：重大级强制人类确认；标准级由人类确认或主 agent 根据反馈判断。
3. 代码以冻结的 `prd.md` + `design.md` 为准；实现导致设计/需求变化时**必须回写文档**，禁止只改代码不改文档。
4. 测试用例由测试工程师独立设计维护，开发者不得覆盖。
5. 质量合规审查员终审通过前不得合并。
6. API、权限、安全配置、Dockerfile/编排文件变更须人类确认。

## 5. 状态更新

- 各角色只更新自身职责范围内的 `tasks.md` 状态（✅/🚧），不动其他角色的条目。
- 跨角色阻塞项由协调员统一标注 `⛔` 并注明原因与 Owner。

## 6. 内容编号

统一前缀：功能需求 `FR-`、非功能需求 `NFR-`、总体规范 `GR-`、接口规范 `API-`、
用户故事 `US-`、验收条件 `AC-`、单元测试 `TC-UT-`、集成测试 `TC-IT-`、
端到端测试 `TC-E2E-`、冒烟测试 `TC-SMOKE-`。编号在变更包内连续、无重复、可交叉引用。

## 7. 文档同步

子模块文档更新后，必须同步更新系统级文档（如 `docs/system/`、项目根 `CLAUDE.md`、
`docs/README.md` 索引），保持变更包与全局文档一致。API、数据模型、角色/权限、
生命周期等变更均需回写对应总体文档。

## 8. 编排

多阶段执行可配合标准 workflow（立项 → 设计 → 实施 → 验证 → 门禁，冻结点为人工确认卡点）。
workflow 的编写规范见 `workflow-authoring` skill。
